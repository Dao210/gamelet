# Gamelet Patches 类谜题方案：复用现有架构与文件题库

日期：2026-09-07。状态：功能实现与本地验收完成（2026-09-07）；线上流量和真实设备性能待发布后验证。详见 [交付记录](patches-implementation.md)。本文保留已批准的范围和验收标准。

## 1. 已确定的约束

沿用 Gamelet 当前 Next.js / React / TypeScript 架构和现有游戏接入方式。题库由项目内配置文件管理，随代码构建和发布。

- 页面仍放在 app/[locale]/patches/，组件放在 components/patches/，规则和题库放在 lib/patches/。
- 复用当前 layout、Navigation、Footer、next-intl Provider、SEO helper、统计函数和部署流程。
- 不调整公共布局、路由分组、全站状态管理、广告策略、全站语言包加载或基础设施。
- 不新增数据库表、Prisma/Drizzle 模型、题库接口、对象存储、独立 CDN 配置或后台服务。
- 题目生成和完整求解只作为开发/发布前工具运行，正式游戏读取已验证配置；首期不需要运行时生成器或 Web Worker。
- 玩家进度用 localStorage 保存；题库不进入数据库，也不以 IndexedDB 作为题目来源。
- 对已有文件的修改限于首页游戏入口、sitemap 和游戏翻译等常规接入项。保留已有 Pulsefront 改动。

已按用户“执行吧 / 继续”的指令实施下述范围。

## 2. 现有项目已经有可复用模式

当前 lib/mirror-maze-levels.ts 导出带 MazeLevel 类型的题目数组；lib/mirror-maze-engine.ts 负责规则；app/[locale]/mirror-maze/page.tsx 引入组件并调用 createPageMetadata。

新游戏沿用同样的关系：页面 → 游戏组件 → 规则引擎 + 配置题库。题量变大后，只在新游戏内部把配置拆成多个文件，按需加载，不改变应用架构。

## 3. 首发产品

首发 Gamelet 自有的 Patches 类矩形分区谜题，提供原创题面和教学。页面如提及 LinkedIn，应明确独立开发关系。

规则：
- 使用轴对齐矩形覆盖整个棋盘，每格只属于一个矩形。
- 每个矩形恰好包含一个线索格。
- 数字表示面积；可以没有数字。
- square 要求宽高相同，wide 要求宽大于高，tall 要求高大于宽，any 表示任意矩形。
- 面积和形状可单独给出、同时给出或都省略；省略内容的线索格仍须可辨认。
- 例如“6 + wide”允许 3×2 或 6×1，不允许 2×3。any 不允许任意多边形。

这一范围参考 [Patches 官方规则](https://www.linkedin.com/help/linkedin/answer/a10314037)，使用独立配置和规则版本。

| 模式/功能 | 方案 |
| --- | --- |
| 自由练习 | 无每日次数限制，连续读取已配置题目；优先未完成题 |
| 每日挑战 | UTC 日期与难度对应配置中的固定题目 ID |
| 渐进教学 | 12 个教学微关卡、60 道精选练习，逐步学习面积、形状和候选排除 |
| 难度 | Easy / Medium / Hard；首发 5×5、6×6、8×8，评级依据推理复杂度 |
| 操作 | 拖动绘制、点击两角、键盘操作、删除、撤销、重做、重置 |
| 提示 | 使用配置内已经验证的解释步骤，分层展示原因与可确定区域 |
| 存档 | 自动恢复当前题、已画矩形、用时、难度与提示次数 |
| 分享 | 用稳定题目 ID 分享同一道题，成绩文本不显示答案 |

“无限练习”表示可以不限次数地玩；配置题库是有限的。完成所有配置题后明确提示已完成本批题，可选择复习；不宣称无限不重复，也不依靠旋转/镜像伪装成新的题目。

账号同步、公共排行榜、实时对战、玩家发布题目、付费系统和 Pips 完整实现不属于首期。

## 4. 配置文件组织

建议采用 TypeScript 数据对象，与项目现有题库写法保持一致，使用 readonly 与 satisfies 检查字段。题目不是可执行脚本：文件只导出数据，不包含取当前时间、随机生成或网络请求等副作用。

建议目录：

```text
app/[locale]/patches/page.tsx
app/[locale]/patches/how-to-play/page.tsx
app/[locale]/patches/strategy/page.tsx
app/[locale]/patches/[difficulty]/page.tsx
components/patches/PatchesGame.tsx
components/patches/PatchesBoard.tsx
components/patches/patches.module.css
lib/patches/types.ts
lib/patches/engine.ts
lib/patches/progress.ts
lib/patches/level-loader.ts
lib/patches/levels/starter-{easy,medium,hard}.ts
lib/patches/levels/catalog.ts
lib/patches/levels/tutorial.ts
lib/patches/levels/easy-01.ts
lib/patches/levels/medium-01.ts
lib/patches/levels/hard-01.ts
lib/patches/levels/daily-2026-09.ts
scripts/puzzles/generate-patches.mjs
scripts/puzzles/verify-patches.mjs
__tests__/lib/patches/
__tests__/components/PatchesGame.test.tsx
```

这里只新增功能自己的目录。首页仍在原位置，旧游戏与公共文件不迁移。

每题配置包含：

| 字段 | 用途 |
| --- | --- |
| id | 永久稳定的题目编号，例如 patches-easy-0001 |
| puzzleVersion / rulesetVersion | 题面版本与规则版本，保证存档和历史链接能识别 |
| rows / cols | 棋盘尺寸 |
| difficulty / techniqueTags | 难度及训练技巧 |
| clues | 每个线索的位置、可空面积和形状约束 |
| solution | 已验证的完整矩形分区 |
| hintSteps | 提示的规则编号、前置条件、相关区域与解释参数 |

提示采用稳定规则编号和结构化参数，文案放入现有 messages/*.json。不同语言共用同一题库，不复制五份棋盘数据。

catalog 只记录题目 ID、所在分包、难度等小型索引；不能从 catalog 静态导入所有完整题包。

## 5. 文件题库的生产与更新

题库流程为：

生成或手工编写配置 → 结构检查 → 唯一解检查 → 逻辑提示校验 → 人工试玩 → 提交文件 → 使用现有流程构建发布。

生成脚本是内容制作工具；即使不运行生成脚本，也可以直接维护配置文件。生成器、完整求解器和验证工具只供 scripts/测试使用，不进入浏览器游戏依赖。

质量要求：
- 所有线索坐标、面积和形状合法。
- solution 无重叠、无空格，满足所有题面约束。
- 精确求解器完整确认只有一个解；发现第二个解拒绝，达到计算预算返回 unknown 并拒绝。
- 独立逻辑推导器能回放所有 hintSteps；只有能靠已支持的推导规则完成，才标记“无需猜测”。
- 用小棋盘独立枚举器交叉验证求解器，避免同一个错误同时出现在出题和验题中。
- 难度由推理技巧、依赖链与人工试玩共同确定，不能只看尺寸。
- 发布前排除等价旋转/镜像重复；旋转时 wide/tall 必须同步转换。
- 已发布 ID 不改题面。修正题目发布新版本/ID，并保留旧配置或明确迁移规则。

首发内容目标沿用：12 个教学微关卡、60 道人工试玩精选题、至少 1,200 道机器验证题。其中预留 270 道给未来 90 天的三档每日挑战。数量为实施目标，不能以降低正确性和讲解质量换取数量。

每次补题只新增配置分包、更新 catalog 和后续每日排期，然后按现有发布流程部署。配置更新需要构建发布，不承诺不发布即可热更新。当前只写方案，不创建任何定时任务。

## 6. 加载和交互性能

优化限定在新游戏内部。

### 6.1 首局与分包

- 页面随现有渲染流程提供一题固定 starter，不等接口、不现场出题。
- 服务端和客户端使用相同 initialPuzzle，避免两侧随机数或日期不同导致 hydration 不一致。
- 游戏开始可操作后，按当前难度通过明确的动态 import 加载对应配置分包；分包资源由现有 Next.js 静态资源路径提供。
- 每包约 50–100 题，按实际压缩体积调整，不把 1,200 道题一次性导入游戏组件。
- 提前准备下一题；只在接近当前分包结尾时加载下一个包。
- 教程、详细解析只在打开时加载；不新建接口或绕过当前部署配置。
- 加载失败时继续保留当前题，提供重试和已加载题复习；不能让整个棋盘报错退出。

### 6.2 本地交互

- 规则引擎使用纯 TypeScript，独立测试，不依赖 React、DOM 或数据库。
- 棋盘使用 HTML/CSS Grid 和轻量 SVG 覆盖层，沿用现有样式系统。
- 拖动预览最多每帧更新一次，只有完成绘制才提交游戏状态与撤销历史。
- 覆盖检查、线索检查、完成判定在有限的 8×8 棋盘上执行；不在拖动中进行完整求解。
- 计时显示独立更新，隐藏页面暂停；高频指针事件不写存档、不发送统计。
- 游戏内无新动画引擎、Canvas/WebGL 框架或全局状态仓库。
- 支持 pointercancel、键盘、点击两角、触屏、读屏和 reduced-motion。

### 6.3 配置提示

题库保证唯一解，因此可以用已验证 solution 检查玩家已提交矩形是否与最终解兼容；该检查不需要运行完整求解器。

- 若当前矩形与唯一解不兼容，提示指出需要重新检查的区域，不强行填入下一块。
- 优先使用其前提在当前状态已验证的 hintSteps。玩家操作顺序不同，不应简单按数组下标弹出下一句。
- 尚不能解释的状态先提供相关规则或完整逐步讲解入口，不声称已经推导出某块。
- 主动选择“查看答案”与普通提示分开，成绩记录 assisted。
- 答案随静态题库可被技术用户查看，因此本地成绩用于个人练习，不作为可信竞赛成绩。

### 6.4 预算与边界

以下是待验收目标，测量使用生产构建、固定测试设备与相同网络条件。

| 指标 | 目标 |
| --- | --- |
| 游戏专属首屏主线程 JS 增量 | gzip ≤ 45 KiB |
| 首题题面及所需数据 | gzip ≤ 5 KiB |
| 单个按需题包 | gzip ≤ 40 KiB |
| 缓冲命中时点击下一题到可操作 | p95 ≤ 100 ms |
| 单步规则校验，最大 8×8 | p95 ≤ 2 ms |
| 拖动中游戏引起的长任务 | 无 ≥ 50 ms 长任务 |
| 游戏棋盘操作导致的布局偏移 | 目标为 0 |
| 移动端 | 390px 无页面横向溢出，操作不中断正常页面交互 |

新游戏只控制自己的增量。整页 LCP、INP、CLS 仍然测量并报告，包含当前公共组件与第三方脚本；目标参考 LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1 的 p75 水平，不把这些整页指标当作已实现的承诺。[指标定义](https://web.dev/articles/vitals)

如果实测瓶颈来自当前公共架构，报告证据与影响，不借此修改用户要求保留的公共架构。上一版的整页 180 KiB 预算、强制 SSG 改造和 CDN 指标不再作为本次必须重构才能通过的条件。

## 7. 每日挑战与进度

daily 配置按月份保存“UTC 日期 → Easy/Medium/Hard 题目 ID”的固定映射。

- 浏览器挂载后按本机 UTC 日期查表，界面显示正在玩的日期和 UTC 刷新规则。
- 页面初始渲染不依赖浏览器日期；先显示一致的 starter，用户进入每日模式后选出当日题。
- 日期与题目映射固定，不使用 dateHash % 当前题库长度，新增题目不改变历史题。
- 已开局的题不在零点强制切换；完成或返回模式选择后提示新日期。
- 本方案没有时间服务，设备时钟错误可能选错当天题。这是免服务端校时的明确边界，不声称具备防改时钟能力。
- 排期不足时显示“新每日题尚未配置，可继续练习”；不得悄悄用昨天题计为今天完成。
- 构建验证检查排期覆盖、引用题目是否存在、规则版本和跨难度配置。

进度使用现有游戏同类的 localStorage 方式，键名独立，例如 gamelet:patches:progress:v1。

- 保存当前题 ID/版本、已提交矩形、难度、计时、提示次数及完成记录。
- 只在有语义的动作后合并保存，离开页面时尽力补写；拖动预览不保存。
- 字段校验、损坏数据、存储被禁用和配额不足均有降级，存档失败不阻止继续游戏。
- 同题多标签页冲突不得在玩家操作时静默覆盖。
- 分享地址采用 /en/patches#p=patches-easy-0001，按 catalog 加载原题；未知 ID 提示后进入正常练习。
- 不承诺跨设备自动同步或刷新后的完整离线启动；已加载题可在当前页面断网继续。

## 8. 现有项目接入与搜索内容

常规改动：
1. 新增 app/[locale]/patches/page.tsx，复用 createPageMetadata。
2. 新增 components/patches 和 lib/patches，不改其他游戏引擎。
3. 在 GameCollectionHome 的现有数组增加游戏卡片。
4. 在 app/sitemap.ts 增加实际发布的页面。
5. 在 messages 中补齐新游戏与首页卡片翻译，沿用当前公开/隐藏语言策略。
6. 用现有 trackGameEvent 等函数记录开局、完成、提示和下一题，不改全站统计策略。

英文为主要搜索验证语言，公开页面按项目现状完成 en、zh、de、es、ja；隐藏语言遵守已有回退和索引规则。题库中不放大段翻译文本，复用 messages 中的技巧和提示模板。

第一批页面以主游戏页为核心；玩法、策略及三档难度页面在内容齐备后一起发布。每日挑战作为主游戏内模式，不新增今日题接口或仅有日期差异的搜索页面。

每个独立页面提供真实不同的内容和对应练习，复用当前 canonical/hreflang 方式；分享 fragment 不进入 sitemap。不批量创建随机 seed 页面，不复制平台原题或以不存在的玩家评分填充结构化数据。

流量方向仍是选品假设。上线后利用现有统计与可用的 Search Console 观察曝光、点击、开局、完成及再次游玩；不以开发完成代替流量验证。

## 10. 实施顺序

| 阶段 | 工作 | 交付条件 |
| --- | --- | --- |
| 1 | 规则类型、引擎、配置格式、首批手工题 | 规则和配置测试通过，不改公共架构 |
| 2 | 题库制作/验证工具、分包、教学和排期 | 配置质量验证通过，已有流程可以构建 |
| 3 | 完整组件、提示、存档、分享和移动端操作 | 浏览器可完整游玩，异常路径有降级 |
| 4 | 首页、SEO、翻译和现有事件接入 | 常规接入完成，性能与回归验收通过 |

上一版包含公共架构调整的人日估算作废；按收敛后范围，在题库生成通过率与人工编辑量明确后重新估算。

后续 Pips 继续采用“页面 + 组件 + 独立引擎 + 配置题库”的相同方式接入。届时复用已经证明适用的小工具，不提前建设跨游戏平台或通用插件框架。
